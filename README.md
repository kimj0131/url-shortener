# URL Shortener Service

Java Spring Boot 기반의 URL 단축 서비스 프로젝트입니다.


간단한 기능 구현으로 시작하여 대규모 트래픽 처리를 고려한 분산 환경 설계를 목표로 하고 있습니다.


## Tech Stack

- Java 17
- Spring Boot 4.x
- Spring Data JPA
- Database: MySQL (로컬 개발 환경에서는 H2 사용)
- Message Queue: Apache Kafka
- Build Tool: Gradle

## Development Environment
- **IDE**: IntelliJ IDEA
- **Version Control**: Git
- **AI Assistant**: Google Gemini (Code Review & Refactoring)

## ⚙️ Performance Report

### 1차 테스트 (Baseline)
*   **테스트 환경:** 로컬 개발 환경 (Apache Bench(ab) 사용)
*   **조건:** 요청 1,000건 (동시 접속 10)
*   **현재 상태:** Redis 캐시를 적용했으나, 로그 저장 로직에서 **DB 조회(SELECT)가 1회 발생**하는 것을 확인했습니다.
*   **측정 결과:**
    *   **TPS:** 약 348 (초당 처리 건수)
    *   **평균 응답 시간:** 약 28ms
*   **회고:**
    Redis를 썼는데도 생각보다 TPS가 낮게 나와서 로그를 분석해보니, 비동기 처리 중에도 불필요한 DB 조회가 발생하고 있었습니다.
    이 부분을 최적화하면 성능을 더 끌어올릴 수 있을 것 같아, 캐시 구조를 개선해볼 예정입니다.

### 2차 테스트 (개선 후)
*   **변경 사항:** `UrlCacheDto` 도입 및 `getReferenceById` 활용으로 리다이렉트 시 **DB 조회(SELECT) 0회** 처리.
*   **결과:**
    *   **TPS:** 441.80 (초당 처리 건수) (**약 27% 향상**)
    *   **평균 응답 시간:** 약 22.6ms
*   **결론:**
    불필요한 DB 조회를 제거함으로써 처리량을 비약적으로 상승시켰습니다.
    이제 리다이렉트 로직은 DB 부하 없이 Redis와 비동기 INSERT만으로 동작합니다.
> **Note:** JVM Warm-up이 완료된 상태에서 재측정 시 최대 **726 TPS (약 108% 향상)** 까지 성능이 향상됨을 확인했습니다.

## Design Decisions
개발 과정에서 고민한 기술적 문제와 의사결정 과정을 기록하고 있습니다.

### - URL 단축 전략 (UUID -> Base62 전환)
초기에는 UUID(8자리)를 사용했으나, 더 짧은 URL과 성능 최적화를 위해 **Base62 알고리즘**으로 전환했습니다.

* **초기 모델 (UUID):** `java.util.UUID`를 사용하여 8자리 문자열 생성.
    * **한계:** 충돌 가능성이 존재하고, URL 길이가 상대적으로 김.
* **현재 모델 (Base62):** DB의 자동 할당 ID를 Base62(62진수)로 인코딩.
    * **장점:**
        1. **충돌 방지:** DB PK를 사용하므로 유일성 보장.
        2. **길이 단축:** 매우 긴 URL도 단 6글자로 표현 가능.
        3. **성능:** 랜덤 생성 및 재시도 로직 제거.

### - API 응답 통일성
클라이언트와의 협업 효율성을 높이고 시스템의 유지보수성을 강화하기 위해 ApiResponse<T> 래퍼 클래스를 도입하여 응답 포맷을 표준화했습니다.

* **도입 이유:** API마다 응답 구조가 다르면 클라이언트(프론트엔드)에서 예외 처리를 일일이 구현해야 하는 비효율이 발생합니다. 또한, HTTP 상태 코드만으로는 비즈니스 로직의 구체적인 성공/실패 원인을 명확하게 전달하기 어렵다고 판단했습니다.

* **기대 효과:**
  * **예측 가능한 통신:** 성공 여부(success), 메시지(message), 데이터(data)가 항상 동일한 구조로 반환되므로 클라이언트의 응답 처리 로직이 단순화됩니다.
  * **디버깅 효율성:** 에러 발생 시 표준화된 메시지를 통해 문제 원인을 신속하게 파악할 수 있어 유지보수가 용이해집니다.
  * **코드 일관성:** 서버 내부적으로도 공통된 응답 처리 패턴을 사용함으로써 중복 코드를 줄이고 개발 생산성을 높였습니다.

### - 조회 성능 개선(Redis Caching)
반복적인 URL 조회로 인한 데이터베이스 부하를 줄이고 응답 속도를 개선하기 위해 Redis 캐싱을 도입했습니다.

* **도입 이유:** 동일한 단축 URL에 대한 리다이렉트 요청이 빈번하게 발생할 경우, 매번 DB를 조회하는 것은 비효율적입니다.
* **구현 방식:** Spring Data Redis의 @Cacheable을 사용하여 최초 조회 시에만 DB에 접근하고 이후에는 Redis에서 데이터를 반환하도록 구현했습니다.
* **개선 효과:** 
  * AOP 로그 측정 결과, 캐시 적중 시 응답 시간이 단축되었습니다.(예: 500ms -> 10ms)
  * DB 조회 쿼리 발생 빈도가 감소했습니다.

### - 쓰기 성능 개선 (JPQL Optimization → Write-Back & JPQL(2차 개선))
* **문제점:** 기존의 JPA 변경감지(Dirty Checking) 방식은 데이터를 수정하기 위해 반드시 조회(SELECT) 쿼리가 선행되어야 했습니다. 이로 인해 단순 카운트 증가 작업에도 SELECT + UPDATE 두 번의 쿼리가 발생했습니다.
* **해결 방안:** @Modifying과 JPQL을 사용하여 조회 과정 없이 데이터베이스에 직접 UPDATE 쿼리를 날리도록 개선했습니다.
* **개선 효과:** 방문 횟수 증가 시 발생하는 쿼리 수를 2회(SELECT, UPDATE)에서 1회(UPDATE)로 줄여 데이터베이스 부하를 감소시켰습니다.


* **2차 문제점:** 기존의 JPQL만 사용하는 방식은 불필요한 SELECT 쿼리는 제거했지만, 단축 링크 클릭이 발생할 때마다 DB에 UPDATE 쿼리를 날려 트래픽이 폭주할 경우 DB에 심각한 부하를 줄 수 있습니다.
* **해결 방안:**
  1. **Redis 누적:** 단축 링크 클릭 발생 시 DB에 접근하지 않고, Redis의 INCR 명령어를 통해 메모리에서만 카운트를 빠르게 누적시킵니다.
  2. **스케줄링:** 스프링의 @Scheduled를 이용해 1분마다 Redis에 쌓인 카운트를 읽어와, JPQL을 통해 DB에 한 번에 반영합니다.
* **개선 효과:**
  * DB에 대한 UPDATE 쿼리 발생 빈도를 감소시켜 쓰기 병목 현상을 개선했습니다.
  * 사용자 요청에 대한 응답 시간에는 영향을 주지 않으면서 시스템 전체의 처리량을 향상시켰습니다.

### - 접속 이력 저장
사용자의 접속 정보를 기록하는 과정이 리다이렉트 응답 속도에 영향을 주지 않도록 @Async를 사용하여 비동기로 처리했습니다.
* **도입 이유:** 접속 로그 저장은 DB 쓰기 작업이므로 시간이 소요될 수 있으며, 로그 저장 실패가 메인 기능(리다이렉트)의 실패로 이어져서는 안 됩니다.
* **구현 방식:** 
  * saveVisitHistory 메서드를 비동기 스레드에서 실행되도록 분리했습니다.
  * 별도의 AsyncUncaughtExceptionHandler를 구현하여, 비동기 작업 중 발생하는 예외를 감지하고 로그로 기록하도록 설정했습니다.
* **기대 효과:**
  * **리다이렉트 지연 시간 최소화:** DB 쓰기 작업이 완료될 때까지 사용자가 기다릴 필요가 없으므로, 사용자 경험이 향상됩니다.
  * **일관된 서비스 품질 보장:** 대규모 트래픽으로 인해 DB 응답이 일시적으로 지연되더라도, 리다이렉트 기능은 영향을 받지 않습니다.
  * **서비스 안정성 격리:** 로그 저장 로직과 리다이렉트 로직을 격리하여, 통계 시스템의 장애가 메인 서비스(페이지 이동)의 장애로 전파되는 것을 방지했습니다.

### - 대용량 트래픽 처리 (Kafka 도입)
접속 로그 저장 로직을 분리하여 시스템의 안정성을 높이고, 대용량 트래픽 상황에서도 유연하게 대처할 수 있도록 Kafka를 도입했습니다.
* **도입 배경:**
    기존의 `@Async` 비동기 처리는 애플리케이션 서버의 메모리(스레드 풀)에 의존하므로, 트래픽이 폭주하면 서버 자원이 고갈되어 `OutOfMemoryError`가 발생하거나 메인 기능(리다이렉트)까지 문제가 생길 수 있었습니다.
* **해결 방안:**
    * **Producer-Consumer 구조:** 리 다이렉트 요청 시 로그 데이터를 Kafka 토픽으로 전송하고 즉시 응답합니다.
    * **부하 분산:** 별도의 Consumer가 Kafka에서 메시지를 꺼내 DB에 저장하므로, DB 부하가 높을 때도 서버는 영향을 받지 않습니다.
    * **데이터 안정성:** Kafka의 **디스크 기반 저장** 특성을 통해 애플리케이션 서버가 다운되어도 데이터가 유실되지 않으며, 추후 브로커 증설 시 **데이터 복제**를 통해 고가용성을 확보할 수 있습니다.
* **기대 효과:**
    * **결합도 제거:** API 서버와 DB 저장 로직이 분리되었습니다.
    * **확장성:** 추후 로그 분석이나 통계 시스템이 추가되어도, Consumer 그룹만 추가하면 되므로 기존 코드 수정 없이 확장이 가능합니다.

### - 동시성 제어 (Distributed Lock)
다중 서버 환경에서 스케줄러가 중복 실행되어 데이터 정합성이 깨지는 문제를 방지하기 위해 분산 락을 도입했습니다.
 * **문제점:** 서버가 여러 대로 늘어날 경우, visitCountScheduler가 각 서버에서 동시에 실행되어 DB 업데이트가 중복으로 발생할 수 있습니다.
 * **해결 방안:**
   * **Redisson** 라이브러리를 사용하여 Redis 기반의 분산 락을 구현했습니다.
   * **AOP**를 적용하여 비즈니스 로직과 락 제어 로직을 분리하고, @DistributedLock 어노테이션으로 손쉽게 락을 적용할 수 있도록 작성했습니다.
   * **트랜잭션 분리:** 락 획득 후 트랜잭션이 시작되고, 트랜잭션 종료 후 락이 해제되도록 순서를 보장하여 동시성 이슈를 해결했습니다.
 * **참조:**
   * 마켓컬리 기술 블로그 - [풀필먼트 입고 서비스팀에서 분산락을 사용하는 방법](https://helloworld.kurly.com/blog/distributed-redisson-lock/)

### - CI/CD 파이프라인 (GitHub Actions)
코드 품질을 지속적으로 관리하고 안정적인 배포 프로세스를 구축할 수 있는 Github Actions를 도입했습니다.
* **구현:** master 브랜치에 코드가 푸시되거나 PR이 생성될 때마다 자동으로 빌드 및 테스트를 수행하도록 구성했습니다.
* **환경 격리:** Docker Service Container를 활용하여 테스트 환경에서도 Redis를 독립적으로 실행함으로써, 로컬 환경과 동일한 테스트 정합성을 보장했습니다.
* **효과:**
  * 개발자의 로컬 환경에 의존하지 않는 객관적인 코드 검증이 가능합니다.
  * 잘못된 코드가 메인 브랜치에 병합되는 것을 사전에 방지하여 프로젝트의 안정성을 높였습니다.
